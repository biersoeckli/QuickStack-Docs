QuickStack networking has two parts that work together:

- **Internal service hostnames** — how apps and databases in a project find and reach each other.
- **Network policies** — which traffic is actually allowed.

<Callout>
**By default, all apps in a project can communicate with each other and with the internet.** Network policies only change that behaviour once you enable them on an app.
</Callout>

## What you need

- An app with a configured source that you can deploy.
- **Write** permission for the app to change and apply policies.

## Where to find it

Open the app and go to the **Domains & Networking** tab. The **Network Policy** card sits below **Domains** and **Node Ports**.

## Internal service hostnames

Every app and database gets an internal DNS name that resolves only inside the cluster:

```
svc-<app-id>.<project-id>.svc.cluster.local
```

With a specific port:

```
svc-<app-id>.<project-id>.svc.cluster.local:5432
```

QuickStack builds the Kubernetes Service and its ports from the app's **Domains** and its **network policy rules** — there is no separate internal-port setting.

## Open a port for internal traffic

A port becomes reachable inside the cluster when an **ingress network policy rule** targets it on the receiving app.

1. Open the **receiving** app and go to **Domains & Networking** → **Network Policy**.
2. Enable **Network Policies** if it is off.
3. Under **Ingress rules**, click **Add ingress rule**.
4. Select the calling app as **Source** and enter the port the receiving app listens on.
5. Click **Add rule**, then **Save & Apply Changes**.

The service now exposes that port internally.

<Callout>
**You usually don't add both sides**
Network policies are mirrored: adding an egress rule on the calling app creates the matching ingress rule on the target, and vice versa. The counterpart is only written when the other app has network policies enabled and you have write access to it. Review the result in the [network graph](/docs/how-to/networking/project-network-graph).
</Callout>

## Copy a connection string

Instead of typing hostnames by hand, copy the exact internal URL from the rule:

1. Open the app that holds the rule (either side of the connection).
2. In the rule table, click the row's action menu → **Copy internal hostname**.
3. Paste it into the consuming app's environment variables.

{/* SCREENSHOT: Rule row action menu with Copy internal hostname | rule-row-actions.png */}
<img src="/img/docs/managing-apps/network-policies/rule-row-actions.png" alt="Rule row action menu" />

The copied value includes the protocol and port, for example:

```
http://svc-<app-id>.<project-id>.svc.cluster.local:5432
```

### Example connection strings

```
# PostgreSQL
DATABASE_URL=postgres://user:password@svc-app-abc.<project-id>.svc.cluster.local:5432/database

# Redis
REDIS_URL=redis://svc-app-def.<project-id>.svc.cluster.local:6379

# Internal HTTP service
API_BASE_URL=http://svc-app-ghi.<project-id>.svc.cluster.local:3000
```

Set these as [environment variables](/docs/how-to/deployments/redeploy-and-rollbacks#environment-variables) in your app, then deploy.

## Enable network policies

1. Toggle **Network Policies** on. The rule editors appear.
2. Add **Ingress rules** and **Egress rules** as needed (see below).
3. Click **Save & Apply Changes** and confirm.

<Callout type="warn">
**Policies apply immediately**
Saving a network policy reconciles Kubernetes policies for this app and every app it connects to right away. You do not need to redeploy the app.
</Callout>

## Ingress rules — who can access this app?

An ingress rule allows a specific source to reach this app on a specific port.

1. In the **Ingress rules** section, click **Add ingress rule**.
2. Fill in the dialog:

| Field | Description |
|-------|-------------|
| **Project** | The project that contains the source workload |
| **Source** | The app or database allowed to connect |
| **Port** | The port on **this** app that the source may reach (1–65535) |
| **Protocol** | `TCP` or `UDP` |

3. Click **Add rule**.

{/* SCREENSHOT: Add ingress rule dialog | add-ingress-rule-dialog.png */}
<img src="/img/docs/managing-apps/network-policies/add-ingress-rule-dialog.png" alt="Add ingress rule dialog" />

## Egress rules — where can this app connect?

An egress rule allows this app to reach a specific target on a specific port.

1. In the **Egress rules** section, click **Add egress rule**.
2. Fill in **Project**, **Target**, **Port**, and **Protocol** the same way as an ingress rule.
3. Click **Add rule**.

<Callout>
**Recommended port**
When the target is a managed database, QuickStack pre-fills the standard port and shows a **Recommended** badge: MariaDB/MySQL `3306`, MongoDB `27017`, PostgreSQL `5432`, Redis `6379`.
</Callout>

### Internet Access

**Internet Access** is a separate egress switch:

- **On** — the app may open outbound connections to public addresses.
- **Off** — outbound traffic is restricted to the workloads you explicitly allow.

## Rules that QuickStack always adds

Some traffic is always permitted so the platform keeps working. These rules are managed for you and are not shown in the editor:

| Direction | Traffic |
|-----------|---------|
| Ingress + Egress | Replicas of the same app talking to each other |
| Egress | DNS lookups to the cluster DNS service (TCP/UDP 53) |
| Ingress | Traefik, when the app has a domain |
| Ingress | Backup jobs and database-tool containers |
| Egress | The public internet, only when **Internet Access** is on |
| Ingress | Node Ports, when configured |

## Connections are kept in sync

Network policies are bidirectional. When you add an ingress or egress rule between two apps, QuickStack creates the matching counterpart rule on the other side. Deleting a rule removes its counterpart too, so you only configure a connection from one side.

The counterpart is only written when the other app has **Network Policies** enabled and you have write access to it. Otherwise the rule is saved on this side only.

<Callout type="warn">
**You need write access to both sides**
Linking to an app you can only read fails with an authorization error, because QuickStack cannot add the mirrored rule on that app. Ask an administrator to grant write access to the referenced app.
</Callout>

## Cross-project access

Internal hostnames are scoped to a project. To connect workloads across projects, pick the other project in the rule dialog when you add an ingress or egress rule. Cross-project targets appear as dashed edges in the network graph.

## View the connections as a graph

The Network Policy card has a **Rules / Network Graph** toggle. The graph centers on the current app:

- Ingress sources on the left, egress targets on the right.
- Dashed edges for workloads in other projects.
- An **Internet** node for outbound access and the app's configured domains.

To see the whole project at once and create connections by dragging, use the **Graph** tab on the project overview. See [Project Network Graph](/docs/how-to/networking/project-network-graph).

## If an app becomes unreachable

When an app has network policies enabled but no domain and no ingress rule, QuickStack shows a **No inbound traffic configured** warning on the app page. Add a domain or an ingress rule to accept traffic again.

## Common use cases

- Connecting apps to databases (most common)
- Microservice architectures — backend services that should not be publicly accessible
- Sidecar apps (e.g. a proxy or cache layer)

## Troubleshooting

| Symptom | Fix |
|---------|-----|
| Connection refused between apps | Confirm an ingress rule exists on the receiving app for the port it listens on |
| App can't connect to a database | Add an egress rule on the app to the database, or an ingress rule on the database |
| App can't reach the internet | Turn on **Internet Access** in the app's egress rules |
| Another app can't reach this app | Add an ingress rule for that app, or a domain for external traffic |
| Name does not resolve | Verify you copied the full hostname, including the project ID |
| Policy doesn't seem to apply | Open the rule card and confirm there are no unsaved changes; then click **Save & Apply Changes** |
| A rule can't be created | You need write access to the app or database you are referencing |

<Callout>
**Migration from presets**
Older QuickStack versions used fixed policy templates (Allow All, Internet Only, Project Apps Only, Deny All). After upgrading, these are converted to equivalent explicit rules on startup. Review the generated rules in the app's **Domains & Networking** tab.
</Callout>
